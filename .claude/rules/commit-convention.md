# コミットメッセージ規約

## この文書の役割

コミットメッセージの型が、そのまま公開されるバージョン番号を決める。
`main` に push すると `.github/workflows/release.yml` が前回タグ以降のコミットを走査し、
型から次のバージョンを判定してタグと GitHub Release を作成する。

型の選択はリリースそのものなので、判断がぶれないよう基準をここに固定する。
コミットを作るときは必ずこの文書に従う。

## 型と上がる桁

| 型 | 上がる桁 | 使う場面 |
|----|---------|---------|
| `feat:` | minor | 機能・設定・ツールの追加 |
| `fix:` | patch | 動作していない設定の修正 |
| `docs:` | patch | README・ドキュメントのみの変更 |
| `refactor:` | patch | 挙動を変えない整理 |
| `perf:` | patch | 起動時間・描画速度の改善 |
| `test:` | patch | テストの追加・修正 |
| `style:` | patch | 整形のみ（インデント・改行） |
| `chore:` | patch | 依存やバージョンの更新、`.gitignore` |
| `build:` | patch | インストール手順の変更（このリポジトリではほぼ使わない） |
| `ci:` | patch | `.github/workflows/` `.pre-commit-config.yaml` |
| `revert:` | patch | 変更の取り消し |
| 型なし（`add` など） | リリースされない | 使わない |

判定は `release.yml` の `Decide next version` が行う。型を書き忘れるとリリースが発生しないため、
必ず上記いずれかの型で始める。

## 型の選び方（このリポジトリ固有）

- **`feat:`** — 新しいツールの導入（`setup.sh` に `setup_*` 関数を追加）、`zsh/aliases.zsh` への
  エイリアス追加、`wezterm.lua` の `config.keys` へのキーバインド追加、新しい設定項目の追加
- **`fix:`** — 設定が効いていない・エラーが出る状態の修正。「気に入らないから変える」は `fix:` ではなく
  `feat:` または `refactor:`
- **`docs:`** — README のみ。設定変更にともなう README 更新は、設定側の型（`feat:` など）に含めて
  1 コミットにする
- **`chore:`** — Homebrew パッケージのバージョン固定、`.gitignore` の調整
- **`ci:`** — リリースワークフロー、pre-commit の設定

## 破壊的変更の基準

判定基準は **「`git pull && ./setup.sh` だけで追従できるか」**。
手作業が必要なら破壊的変更にあたる。

### 破壊的変更にあたるもの

- `~/.config/` 配下のリンク先・配置の変更（`setup_wezterm` / `setup_starship` / `setup_zsh` /
  `setup_pet` / `setup_lazygit` のリンク先変更）。既存の実体が `.bak` に退避され、
  以前の設定を手で拾い直す必要が出る
- `zsh/hidden/` の場所・ファイル名の変更。Git 管理外のため自動で移行できず、
  PATH や API キーが読まれなくなる
- `zsh/aliases.zsh` の既存エイリアスの**削除**、または同じ名前で別のコマンドに変える変更
- `wezterm/wezterm.lua` の `config.keys` や `zsh/.zshrc` の `bindkey` で、**既存の割り当てを別の操作に変える**変更
- `setup.sh` が要求する前提の変更（新しい必須パッケージ、Homebrew 以外の依存の追加）
- `zsh/keybindings-defaults.tsv` のフォーマット変更（`kb` コマンドの読み取りが壊れる）

### 破壊的変更にあたらないもの

- 新しいツールの追加（既存の設定に触らない）
- エイリアス・キーバインドの**追加**のみ
- 空いているキーへの新規割り当て
- README・コメントの更新
- 挙動が変わらないリファクタリング

## 0.x の間の方針

**現在 0.x 系のため、破壊的変更でも `!` と `BREAKING CHANGE:` は使わない。**

0.x は「設定がまだ固まっていない」ことを示すバージョンであり、この段階で 1.0.0 に上げると
以降の破壊的変更ごとに 2.0.0、3.0.0 と進んでしまう。

破壊的変更を入れるときは型を `feat:` のままにし、本文に影響と対処を書く。

```
feat: hiddenの読み込み先を~/.config/zsh/localに変更

zsh/hidden/ を ~/.config/zsh/local/ に移した。Git 管理外のファイルは自動移行
できないため、既存環境では手でコピーが必要。

注意: 旧 zsh/hidden/*.zsh を ~/.config/zsh/local/ に移してから ./setup.sh を実行する。
```

本文に書く見出しは `注意:` を使う。**行頭に `BREAKING CHANGE:` と書くと `release.yml` が
major と判定して v1.0.0 に飛ぶ**ため、0.x の間はこの文字列を行頭に置かない。

`v1.0.0` は設定が固まったと判断した時点で、Actions の `Release` を手動実行して出す。

```bash
gh workflow run Release -f bump=major
```

1.0.0 以降は `feat!:` や行頭の `BREAKING CHANGE:` を使って major を上げる。
`!` はどの型に付けても major になる（`fix!:` も major）。

## 書き方

- 日本語で書く。1 行目は変更内容がわかる要約にし、句点は付けない
- 1 行目は型を含めて 50 文字程度に収める
- 本文には「なぜ」を書く。「何を」は差分を見ればわかる
- 1 コミット 1 変更。設定変更とその README 更新は同じコミットにまとめる

```
feat: WezTermにLeaderキー操作とタブの色分けを追加

ペイン操作のキーが Cmd と衝突していたため、Leader (Ctrl+a) 配下にまとめた。
タブの色分けは、ペインが増えたときに現在位置を見失わないようにするため。
```

## 注意事項

- マージコミット（`Merge pull request #22 from ...`）は判定対象から除外される。
  通常マージでは個々のコミットメッセージが、squash マージでは squash 後のメッセージが効く
- 複数の型が混ざったコミット群では、いちばん大きい桁が採用される
  （`feat:` と `docs:` が混在 → minor）
- リリースしたくない変更でも、型なしのメッセージは使わない。
  型を付けて patch が増えるほうが、履歴として正しい
